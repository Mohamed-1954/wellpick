A record that disappears from a list can still be reachable. Noloco's docs say this directly: visibility rules and filters change the interface, and the data stays reachable by URL or API. Test what an unauthorized user receives, not what the screen shows. Only test an app you own, with fictional records.

## 1. Build a fixture you can read at a glance

Create two fictional companies, Company A and Company B, with two projects each and obvious labels such as “A-only project”. Add one client user per company, one staff user, an internal-only note and a harmless sample file.

Write the expected rules before you touch the settings:

- Each client reads only its own company's records.
- Neither client can read internal notes or change which company a record belongs to.
- Only the intended role can create, edit or delete each record type.

## 2. Know the rule your product applies

- **Softr:** global data restrictions separate view, create, edit and delete. View restrictions work on every plan; create, edit and delete restrictions need Business. Pro has 3 custom user groups and Business 10. An earlier version of the docs said a “Can't” rule beats a conflicting group rule, and that the restrictions do not cover the Comments block. Test comments on their own.
- **Noloco:** permissions are enforced on the server. Permissions from several roles add up; two record rules inside one role narrow to records that match both. Free has 2 roles; field-level permissions and more roles need Build. Use “View as User”, then repeat the test in a real session.
- **Fillout:** an Airtable update link is a key to the whole record. Anyone who opens it can see every field unless “Restrict prefilled data” is on. A hidden field or prefilled email is context, not proof of who submitted.

## 3. Run the checks in separate sessions

Use separate browser profiles or private windows for A, B and the staff user. An admin preview is not the path a client takes. Record the plan, the date and each user's roles with every run.

Run every cross-client check in both directions: a rule can protect A and still expose B. A rejected edit can still reveal another client's name in its error or picker.

For each row, record the expected outcome, the actual outcome, where the evidence is and which user you were signed in as. Mark PASS only when you observed the expected outcome. Mark FAIL when you did not, BLOCKED when setup was missing, and NOT_RUN when nobody tried. Keep secrets and personal data out of screenshots.

**If a check fails:** stop. Fix the configuration and rerun the whole table. Hiding the route is not a fix. If the control you need is on a higher plan, price that plan in the [cost guide](/guides/portal-costs/) before you compare products. A passing run covers only that configuration and date. Rerun after any change to roles, tables or file storage.

## 4. Check the limit you will hit first

What happens at each limit, per the vendors' docs:

- **Softr users:** Free allows 5 app users in total. Basic allows 5 team and 5 client users, and you cannot buy more. Past a plan's maximum, new users are created but stay deactivated. That means a client can be invited and still be unable to sign in. Staff on Gmail count as client users.
- **Noloco seats:** a user takes a seat once they log in. Deactivating a user frees the seat from the next billing cycle, and the records stay.
- **Noloco workflows:** Free allows 100 runs a month, then workflows stop. Build includes 3,000; extra runs continue and are billed.
- **Fillout responses:** over the monthly limit, forms keep collecting. You then upgrade, buy bulk submissions or wait for the next month.

**Checkpoint:** for each product, write down the limit you are closest to and who gets told when you reach it.

## 5. Name who can switch it off

Name one person for each of these:

- approving permission changes;
- chasing a missing form response;
- fixing a broken record link or a wrong notification;
- billing and renewal;
- pausing access or reversing a bad change.

Write down the route for “a client saw the wrong project”: who pauses access, how the change is reversed, and whether your export is usable. Noloco documents CSV exports that keep linked-record IDs, but a CSV is records, not a whole app. Records in Airtable stay in Airtable.

## 6. Send an invitation that sets expectations

Tell the client what the portal is for, the first thing to do, who to contact when access fails, and which channel to use for anything urgent. A pattern to adapt:

> Your project workspace is ready. Open it and check the project brief. If anything is wrong, reply to your project contact before approving it.

Record “invited” as an event. It does not prove the client logged in.

## 7. Invite one client, then review

Invite one friendly client first. After their first real week, check four things. Where did they stop? Which submissions arrived incomplete? Did internal notes stay internal? Did the promised process happen? If a boundary fails, disable the exposed path first, tell the internal owner, fix the setup and rerun section 3 before you invite anyone else.
